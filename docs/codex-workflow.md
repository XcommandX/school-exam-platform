# 三人使用 Codex 的工作方式

## 让 Codex 访问项目

每位开发者使用自己的 GitHub 账号获得仓库访问权，将仓库克隆到本机，再在 Codex 中打开该文件夹作为本地项目。Codex 在获得本地文件访问权限后可读取、修改并运行项目；推送到私有仓库仍需要该开发者的 GitHub 写入权限和登录授权。

GitHub 仓库不必公开，才能供本地 Codex 开发。三人的聊天记录不作为共享知识来源，项目决定应写入仓库文档。

如果以后使用 Codex 云端任务，需要单独检查 GitHub 仓库授权、云端环境和依赖安装配置。连接一个集成不代表所有本地工具和云端环境均已获得同样权限。

## 第一次开始任务

可向 Codex 提供下面的请求，并补充具体目标：

> 请读取 README.md、AGENTS.md、CONTRIBUTING.md 和任务相关文档，检查当前分支及未提交改动。我的任务是【目标】，验收条件是【可观察的结果】。在独立功能分支完成实现，保留其他人的改动，运行实际适用的检查，并说明改动与验证结果。如需改变公共登录、数据结构或跨模块接口，请同步更新文档并解释影响。

## 源码首次接入

> 请按 docs/source-intake.md 检查【源码仓库或本地目录】，记录原始版本、技术栈、运行方式、配置与数据存储。先验证原有主要功能，再提出接入统一网站的改动。将核实结果更新到文档中，区分已验证事实与建议。

## 分工方式

任务可按 SAT、托福、公共登录与答题记录划分，具体由谁负责在 Issue 中约定。公共接口变动需要通知使用该接口的任务负责人，并在 PR 中写明迁移步骤。

同一开发者同时运行多个 Codex 任务时，建议使用不同 Git worktree 或独立工作副本，避免多个任务同时修改同一工作目录。

## 合并前交付

- 说明用户可观察到的变化。
- 附上实际检查结果、必要的界面证据和复现步骤。
- 说明是否修改配置、数据结构、权限或其他模块接口。
- 将未完成事项和后续任务写入 PR 或 Issue。

Codex 的代码生成完成不等于网站已成功部署。必须分别确认应用能运行、检查通过和部署可访问。
